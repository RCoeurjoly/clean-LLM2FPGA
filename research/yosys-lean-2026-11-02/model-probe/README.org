#+title: Whole-model frontend coverage probe
#+date: 2026-11-02

* Result and scope

This section records the initial frontend-only probe. The subsequent
[[file:../torchlean-import-run/runbook.org][built TorchLean attempt]] uses the actual Lean-generated adapter and
confirms the same whole-model embedding failure. Its two small controls
pass typed import and numerical reference execution in Lean, with seven
matching Float32 output words. The full model remains unimported.

The existing quantized TinyStories artifact loads and runs in its original
PyTorch environment. The TorchLean frontend attempt stops at
=aten.embedding.default=. A scan of all 1,429 call nodes identifies
315 rejected call sites across 18 of the graph's 35 operator identities.
The graph has 1,710 total nodes, including 280 placeholders and one output.

*No Lean checker or all-input equivalence proof ran in the initial probe.*
Lean/Lake had not yet been installed then. That spike reconstructed the default Python
capture adapter from the pinned upstream Lean string emitter, using the
small explicit evaluator in [[file:extract_adapter.py][extract_adapter.py]]. It rejects unfamiliar
emitter syntax and does not add or change operator rules. The generated
[[file:capture_adapter.py][adapter]] passes Python parsing, a supported addition control captures
successfully, and six minimized frontend cases reproduce failures.
This is frontend diagnosis, not a completed import into a built Lean
environment. Recheck with the upstream Lean-generated adapter when that
environment is available.

The captured original graph and the full-model failed re-export path are
different views: the coverage scan inspects every call in the original
saved graph, while the whole frontend follows TorchLean's re-export-first
entry point. Both fail on embedding as expected, but later coverage
counts are not a claim about a fully serialized or type-checked program.

* Observed blockers

| Feature | Rejected calls | Meaning of the observed failure |
|---------+----------------+---------------------------------|
| Embedding | 2 | No lowering for =aten.embedding.default=; first whole-import failure. |
| Dynamic qparameters | 33 | Tuple-valued =quantized_decomposed.choose_qparams.tensor= lacks lowering. |
| Rounding | 33 | =aten.round.default= lacks lowering. |
| Clamping | 115 | =aten.clamp.default= lacks lowering. |
| Linear payload resolution | 49 | Existing Linear rule cannot resolve computed weight =transpose= nodes into its frozen payload. |
| Metadata assertion variant | 24 | Positional schema variant rejected; 230 other metadata assertions are recognized. |
| Dropout | 25 | Saved calls use =(p=0.0, train=False)=; an identity rule would still need a justified contract. |
| Selection | 8 | =aten.where.self= lacks lowering. |
| Other shape, factory, comparison, alias/mutation operations | 26 | arange/default+start, unsqueeze, full, triu, gt, mul_, expand, lift_fresh_copy, detach_. |

All 49 Linear weight operands have dependency closures involving only
frozen state, according to graph data dependencies. This suggests checked
constant evaluation or a more general Linear rule as alternatives; the
probe does not prove either transformation correct. The minimized Linear
case uses a runtime weight to isolate the payload restriction, whereas the
original-shaped regression retains the actual frozen-state closure.

The remaining 884 calls are recognized by lowering rules and 230 by the
metadata handler. Recognition does not establish serialization success,
type checking, numerical correspondence, or proof scalability. The
present measured bottleneck is frontend coverage. Solver/proof scaling
remains unmeasured.

* Hardware probe results

These are the initial capped-probe results. The subsequent
[[file:../full-hardware-run/runbook.org][full-machine reproduction]] rebuilt both generic production checkpoints
and completed full-model FunctionalIR/JSON export, import and Lean
compilation on this same machine.
It also established the current cached netlist's dependency lineage to
the exact RTL input, and compiled and trace-checked the small memory model.

The actual generated =core.sv= is 41,783,062 bytes. Together with its
production =model.sv= and =memory.sv=, it was processed using the project
Yosys 0.62 executable recorded in [[file:hardware-results/report.json][the hardware report]]. The process
aborted with =std::bad_alloc= during =PROC_DLATCH= after about 80 seconds
under a *6 GiB address-space cap*. It had not reached FunctionalIR export
or Lean import. This is a measured failure under that resource envelope,
not evidence of a fundamental scaling limit or a failure of the Lean
importer. The exact command sequence and compressed diagnostic log are
retained in [[file:hardware-results/export.ys][export.ys]] and [[file:hardware-results/yosys.log.gz][yosys.log.gz]].

The frontend was built-in =read_verilog -sv=, not =yosys-slang=. The
current [[file:../../../nix/direct/rtlil.nix::5][production recipe]] and [[file:../../../build/full-model/17-synthesis.log::8][earlier synthesis command]] use the same
frontend. The probe had already parsed and elaborated the design when it
failed during process lowering. A [[file:../../../build/full-model/27-native-ram-and-json.log::12021][successful production RAM-mapping run]]
reports 15,312.60 MB peak memory and 24,440 =RAMB36E1= / 430 =RAMB18E1=
cells, followed by successful JSON export. Those earlier runs have not
been established to use byte-identical RTL to this probe. The 6 GiB cap
was our experimental choice and is below the reported resource demand
of that successful flow. It does not demonstrate a new RTL-consumption
or Lean-import limitation.

The workspace also contains a 3,350,533,882-byte RAM-stage RTLIL file and
a 4,022,901,774-byte final JSON netlist. Their lineage was not freshly
revalidated against the probed RTL. Their sizes illustrate why a compact
earlier representation, retained memories, streaming readers, and
hierarchical proof boundaries deserve priority over generic full-file
JSON parsing or Boolean expansion.

Following the minimal-reproducer approach, the unchanged production
=model_memory= module was tested separately with its default 16 words.
Yosys normalization, FunctionalIR SMT-LIB export with matching JSON, and
the =xiangshan2Lean= Python importer/Lean emitter all completed. The model
contains *one memory, 11 state fields, and 79 expression nodes*. The
generated source represents memory as an address-to-word function.

The exact upstream =expose_arbitrary= helper is required between
normalization and FunctionalIR export. A first stripped-down memory
attempt omitted that step and hit a Yosys assertion on =$anyseq=; the
corrected runner exposes those values as explicit inputs, as the upstream
driver does. This was a runner omission, not evidence of an upstream bug.
