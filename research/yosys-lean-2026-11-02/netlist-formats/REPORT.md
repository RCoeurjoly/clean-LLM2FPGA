# Lean support for Yosys netlist exports — 2026-11-02

The strongest source-verified result in this part of the survey is **deepai-org/loom's actual Yosys JSON adapter**. It reads Yosys `modules`, `netnames`, `cells`, `connections`, and `parameters`, translates them to a neutral JSON schema, and passes that through Lean parsing and checked lowering into executable hardware semantics. This is substantially more than finding a generic JSON library. Its own source explicitly treats Yosys and the Python adapter as untrusted and requires separate source/artifact equivalence evidence. [Adapter](https://github.com/deepai-org/loom/blob/ea1770339296375988b42121db599b4cb36184d7/scripts/yosys_to_loom_ir.py#L1), [Lean importer boundary](https://github.com/deepai-org/loom/blob/ea1770339296375988b42121db599b4cb36184d7/Loom/Hw/ImportIR.lean#L8).

There are several real SV-to-Lean routes, but no inspected implementation establishes a universal, fully proved importer for arbitrary Yosys-generated SystemVerilog. No source-verified Lean importer was found for BLIF/EBLIF, EDIF, JNY, Intersynth, SimpleC, Functional C++, or Yosys connection-table output within the searches and candidate audits below. CXXRTL also lacks an established dedicated bridge. These are bounded negative results, not proofs that no public or private implementation exists.

## What the source actually implements

|---|---|---|
| `write_json` | **deepai-org/loom**, related **deepai-org/lean_hw**, and fork **ssghost/loom**: real Python Yosys-schema adapter → Lean neutral-IR importer → BitVec/register/memory semantics. | Adapter and Yosys remain outside the kernel proof boundary; supported cell subset, explicit two-state/partial-value policies, and external equivalence/signoff are required. The related projects are not independent corroborating implementations. |
| `write_json` | **ErosSph/xiangshan2Lean** uses matching JSON for metadata, effects, normalization and known initial bits. | Transfer semantics are imported from `write_functional_smt2`, not from JSON alone. Its `.table.json` is its own Lean execution interface, **not** Yosys `write_table`. |
| `write_json` | **formalized-si/redstone-verify** reads port metadata from JSON. | Its certified semantic route uses AIGER/LRAT; port extraction is not a general JSON semantic importer. |
| `write_verilog` / `-sv` | **thomasnormal/lean-surfaces** has a substantial pyslang 11.x external-source extractor, custom `sv-0.1` envelope, four-state values and cycle/timed interpreters. | The envelope is not Yosys JSON. Python/slang extraction remains trusted. M0 cycles use an implicit single rising edge; cycle/timed adequacy is explicitly stated rather than generally proved. Unsupported constructs and scheduler tiers matter. |
| `write_verilog` / `-sv` | **ErosSph/leap** has a pinned pyslang 11.0.0 parser, Python IR and Lean code generation. | Two-state supported RTL subset; Lean 4.26.0; unverified frontend/code generator. Its model-level theorem corpus is not an RTL/model translation theorem. |
| `write_verilog` / `-sv` | **muzafferkal/circuitprover-sv** translates a restricted symbolic-parameter SV subset to Lean step/output functions. | Regex source parser; generator rejects `always_comb`, inout and unsupported width/statement forms. Exhaustive small-width co-simulation does not prove the translator for every width. |
| `write_verilog` / `-sv` | **Verilean/sparkle** has a real Lean parser and lowering pipeline. | Failed always blocks can be skipped, missing modules can be replaced with warning wires, unsupported verification expressions generate `sorry`, and assertion macros can generate `by sorry`. All 18 inspected parser-bearing forks retained the three principal parser/lowering/proof-emission gaps. |
| `write_verilog` / `-sv` | **nathsou/HDLean** proves parsing/printing and graph execution for its own emitted SV grammar. | This is a rigid AAG-derived syntax with generated `hd_top`/`hd_m_*`, `HD_GATES`, and `HD_LITERALS` scaffolding; it is not an arbitrary Yosys SV reader. **Easyoakland/HDLean** is a separate output compiler. |
| Verilog-like syntax | **verilog-proof/VerilLean** supplies Lean `v![...]` syntax and operational/transition semantics. | Literal apostrophes become `#` to fit Lean's lexer. This is not unchanged external-file ingestion. **CircuitHDL**, **VLean**, and HDL-generating projects likewise must not be counted merely because they contain Verilog-flavoured syntax. |
| `write_spice` | **lean-surfaces** has a real direct Lean SPICE parser, hierarchical `.subckt`/`X` expansion, linear circuits and a restricted Level-1 MOS model. | No Yosys bridge was established. The parser rejects unsupported cards such as `.include`; elaboration requires ground and its supported model profile. |
| CXXRTL/C++ | **lean-surfaces** has adjacent Clang translation/evidence and narrow C++ value/callable machinery. | No CXXRTL runtime/header/scheduling bridge was found. Generic C++ support is not CXXRTL support. |

## Important exclusions and proof qualifications

**digama0/thinking-sand** performs useful external netlist analysis, but its Lean `theNetlist`, `nStateN`, and `celltopoCert` are axioms. It therefore does not provide a kernel-checked import of the actual Yosys file. **COS598B-Final-Project-Verilog-To-Lean** is an LLM translation/compiler-conformance benchmark; compiling its generated model does not prove fidelity to Verilog. [Thinking Sand object](https://github.com/digama0/thinking-sand/blob/5a24f5ea179ff5fbca24e01659f78a6330b846b1/lean/ThinkingSand/L2/NetlistObject/Basic.lean#L15), [benchmark checker](https://github.com/soohyuk-cho/COS598B-Final-Project-Verilog-To-Lean/blob/38aad0ea8f4af85c5b470df0a2f114d4f29b6d48/check.py).

Sparkle's identified gaps are executable source paths, not interpretations of README wording: [failed always-block skip](https://github.com/Verilean/sparkle/blob/1614cee83ac586ca9a0626cd4af13bfef7347c3a/Tools/SVParser/Parser.lean#L913), [missing-module skip](https://github.com/Verilean/sparkle/blob/1614cee83ac586ca9a0626cd4af13bfef7347c3a/Tools/SVParser/Lower.lean#L2388), [unsupported-expression admission](https://github.com/Verilean/sparkle/blob/1614cee83ac586ca9a0626cd4af13bfef7347c3a/Tools/SVParser/Verify.lean#L232), [assertion admission](https://github.com/Verilean/sparkle/blob/1614cee83ac586ca9a0626cd4af13bfef7347c3a/Tools/SVParser/Macro.lean#L91). [Fork flags](fork-source-flags.json) record all 54 parser/lowering/verification file observations across 18 forks and 16 distinct blobs. Another 11 discovered hardware forks received tree inspection, for 29 fork trees total.

Lean-surfaces has explicit axiom-pin machinery and many substantive semantic lemmas. Its `guardL` tactic error recovery nevertheless logs an exception and calls `g.admit`, so error-free build and declaration-dependency auditing remain essential. This recovery path should not be mistaken for an ordinary successful theorem. Its general cycle/timed adequacy goal is explicitly unproved. [Recovery](https://github.com/thomasnormal/lean-surfaces/blob/c2aaf29b4778bc39b9d09485afe504b33cc92b9d/LeanModels/Sv/CombProcTactic.lean#L470), [axiom pins](https://github.com/thomasnormal/lean-surfaces/blob/c2aaf29b4778bc39b9d09485afe504b33cc92b9d/LeanModels/Sv/PinAxioms.lean#L5), [adequacy status](https://github.com/thomasnormal/lean-surfaces/blob/c2aaf29b4778bc39b9d09485afe504b33cc92b9d/LeanModels/Sv/Adequacy.lean#L45).

## Coverage and reproducibility

The existing **20,707-repository census** was reused without activity, archive or fork exclusions. Local metadata matching found 14 candidates. `candidates.csv`, `curated-hardware.json`, and `source-file-matches.csv` supplied additional hardware leads. This is supplemented by **51 distinct GitHub query families and 71 saved result pages**: **42 query families have all reported result pages, 9 broad/noisy families are explicitly incomplete**. GitHub reported `incomplete_results=false` on these responses; that flag does not remove our own page caps or prove semantic completeness. BLIF counts changed from 256 to 271 while paging, illustrating that the index is not a frozen snapshot. The precise query strings, counts, pages, caps and drift flags are in [query coverage](query-coverage.csv) and [JSON page details](query-coverage.json).

The incomplete families are the unrestricted `Lean yosys` repository query (4,046 hits, first 1,000 retrieved); EDIF/Lean and SimpleC/Lean code probes (mathematical `edifice`/`simpleC` substring collisions); broad Yosys+Lean Python, CXXRTL+Lean and BLIF+Lean code probes; and three noisy mixed-language theorem/SPICE repository probes. Narrower backend commands, reader names, primary-language queries, source-tree inspection and candidate source inspection supplied the substantive findings. No universal exhaustion of GitHub code, repository history, non-default branches, private repositories or unindexed files is claimed.

The source audit scanned **8,919 candidate text files**, with per-pattern hits retained in [local-source-hits.json](local-source-hits.json). No dedicated BLIF, EDIF, CXXRTL, JNY, Intersynth, SimpleC, Functional-C++ or Yosys-table implementation was established. The BLIF mentions were surrounding tooling/landscape references, not a Lean reader. Repository default-branch source trees and relevant full text were inspected at pinned Git commits; old/forked projects were included. Source filenames and metadata matches alone were not treated as semantic support.

Late narrow SPICE code search found a further **LSDL-Standard-Cell-Library** switch-network semantics file: it proves series/parallel transistor-network facts but the inspected file is not a SPICE text parser. Other late hits such as LeaTTa/obend remain limited or unchecked leads; this survey does not infer complete-project absence from those single-file observations. [Limited LSDL evidence](late-spice-evidence.json) records the immutable blob hash. The sole unrestricted CXXRTL/Lean repository hit, `skyp0714/prefetchit`, had no `.lean` files in its 12,101-entry source tree.

`requests.jsonl` records 195 successful read-only `gh api` requests with endpoint, UTC time and local response destination. Raw search pages and fork source/tree responses are gzip-compressed to keep the artifact compact. The GitHub connector repository-search wrapper returned broad irrelevant matches for a flagged query, and its generic fetch endpoint rejected repository-search REST URLs; authenticated `gh api` was therefore used for reproducible exact counts and pagination. The narrow source-index checks are also retained; source search coverage is separate from repository metadata coverage.

Selected source evidence is in `evidence/`; [evidence-manifest.json](evidence-manifest.json) records commit, Git blob SHA, SHA-256 and source URL. Full downloaded source snapshots have been moved to `/tmp/yosys-lean-2026-11-02-netlist-snapshots/` and are located in [snapshot-locations.json](snapshot-locations.json). GitHub query/source fetches can be replayed with `collect.py`; for example `python3 collect.py search`, `python3 collect.py code`, and `python3 collect.py trees`. Its cache reader accepts the compressed raw responses. The final refined query sets are recorded literally in their index/coverage files.

## Verification performed

Two Python Loom adapter probes were executed: a synthetic Yosys `$and` cell produced neutral IR with no blockers, and an unsupported `$mystery` cell produced an explicit blocker. [Probe artifacts](loom-adapter-probes.json) preserve the input and output; this checks the Python adapter only, not Lean proofs or actual Yosys export.

A comment/string-stripped lexical audit covered 89 Loom hardware files, 138 lean-surfaces SV/circuit/SPICE files, 12 VerilLean files, 56 HDLean files, 210 LEAP theorem files and 118 Thinking Sand files. [Raw findings](proof-token-audit.json) include the SV error-recovery admission and Thinking Sand's external axioms. A lexical audit is not a transitive `#print axioms` or kernel replay.

No Lean executable or pyslang installation was available in this worker, so no fresh project build or general parser acceptance test is claimed. The root audit separately exercised the actual production memory RTL through Yosys FunctionalIR plus matching JSON and xiangshan2Lean source generation; that successful source generation is still short of a Lean-checked end-to-end equivalence proof. See the sibling model-probe artifacts for exact input, commands and resource limits.
