#+TITLE: Compiler pipeline — preparation and manual approval loop

* Goal and architectural constraint
Prepare the complete active pipeline for manual, chunk-by-chunk review.
Task 1 selected PyTorch → Torch-MLIR → CIRCT → Verilog → Yosys.
Tasks 2 and 3 establish graph lowering and explicit compiler stages as the
architectural baseline. A model-specific Calyx generator does not establish
that frontend obligation merely by replacing its text rewrites with passes.
On 2026-10-09 the user explicitly required PyTorch graph lowering and approved
the written design. The graph-derived backend is specified in
[[file:../../docs/superpowers/specs/2026-10-09-graph-derived-pipeline-design.md][the graph-derived pipeline design]].
The user also explicitly agreed that expected answers must never construct
the hardware. Design approval does not imply approval of any code chunk.

Semantic transformations must operate on an IR with explicit nodes and
references. Parsing and serialization may recognize and emit text; they must
not silently change computation. Replacing names, expressions, control,
memory implementations or initializers in emitted code is prohibited.

* Loop
1. Inventory every active stage and its transitive code dependencies.
2. For each chunk, document input/output IR, preconditions, invariants and
   unsupported cases; isolate the implementation and remove semantic rewrites.
3. Verify the pass independently, then its composed caller. Invalid inputs
   must fail explicitly. Structural tests alone do not prove arithmetic or
   timing equivalence; use executable reference and RTL checks where relevant.
4. Freeze the review candidate in a commit and provide exact files, reading
   order, evidence and remaining limitations. Mark it ready only after its
   stated checks pass. Agent review is preparation, never human approval.
5. The user reads the chunk and approves it or requests changes. Record the
   decision and commit. Repair requested changes and repeat that chunk.
6. Changes to an approved chunk, its contract or relevant dependencies reopen
   approval. Repeat until every active chunk and final composition is approved.

Historical reproduction code remains identifiable as historical; it cannot
be silently invoked by the repaired production build. New RTL/configuration
does not inherit the old board acceptance.
